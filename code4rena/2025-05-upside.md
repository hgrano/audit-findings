## ⚠️ Medium Severity Findings

### M-01: UpsideProtocol is easily susceptible to sandwich attacks and griefing

#### Description and impact
There is nothing to stop an attacker from buying and selling the meta token within a single block. This allows an attacker to perform a sandwich attack where by:

1. The attacker sees a victim's buy order in the mempool.
1. The attacker submits a transaction which front-runs the victim - buying up the token at the current price.
1. The victim's transaction goes through, but they pay a higher price due to the change in token reserves.
1. The attacker backruns - selling back the tokens they bought at a higher price.

It is also worth nothing that the pricing curve and its parameters on UpsideProtocol.sol#L40-L41, shown below, will cause rapid changes in token price with fairly small amounts of USDC.

```solidity
    uint256 private constant META_COIN_DEFAULT_TOTAL_SUPPLY = 1_000_000 * (10 ** 18);
    uint256 public constant INITIAL_LIQUIDITY_RESERVES = 10_000 * (10 ** 6);
```

This will mean that large amounts of slippage may occur, leading to griefing - as due to front-running, prices increases may cause buy orders to revert. Users may then need to accept larger slippage, hence opening the opportunity for the sandwich attack mentioned above. For reference, I have compiled a table below of how the actual buy output token amounts change as a result of consecutive buys using 500 USDC each time - assuming a buy fee of 1%. Every time the USDC reserves increase from each buy, there is a significant change in price and output token amounts, particularly when there are lower USDC reserves.

### Notes

The judges decision was that, due to the fact there is slippage protection (minimum output amount), this is not a valid issue. Respectfully,
I still see merit in raising this issue because, as shown in the table above, the price changes are significant as the reserves change due to the
small amount of initial USDC reserves. Even with fairly small increments of $500 USDC the output token amounts change rapidly. Therefore buyers may need to accept high slippage otherwise their transactions will revert, making them susceptible to sandwich attacks.

#### Proof of Concept
Replace the contents of PoC.test.ts with the following code:

```solidity
import { HardhatEthersSigner } from "@nomicfoundation/hardhat-ethers/signers";
import { ethers as hhethers } from "hardhat";
import {UpsideMetaCoin, UpsideProtocol, UpsideStakingStub, USDCMock} from "../types";
import { ethers } from "ethers";

describe("C4 PoC Test Suite", function () {
  let signers: HardhatEthersSigner[];
  let owner: HardhatEthersSigner;
  let user1: HardhatEthersSigner;

  let stakingContract: UpsideStakingStub;
  let upsideProtocol: UpsideProtocol;
  let liquidityToken: USDCMock;
  let sampleLinkToken: UpsideMetaCoin;

  before(async function () {
    signers = await hhethers.getSigners();
    owner = signers[2];
    user1 = signers[0];

    const upsideStakingStubFactory = await hhethers.getContractFactory("UpsideStakingStub");
    stakingContract = await upsideStakingStubFactory.connect(owner).deploy(owner.address);
    await stakingContract.connect(owner).setFeeDestinationAddress(owner.address);

    const upsideProtocolFactory = await hhethers.getContractFactory("UpsideProtocol");
    upsideProtocol = await upsideProtocolFactory.connect(owner).deploy(owner.address);

    // Deploy mock USDC
    const liquidityTokenFactory = await hhethers.getContractFactory("USDCMock");
    liquidityToken = await liquidityTokenFactory.connect(owner).deploy();

    // Setup protocol
    await upsideProtocol.connect(owner).init(await liquidityToken.getAddress());
    await upsideProtocol.connect(owner).setStakingContractAddress(await stakingContract.getAddress());

    // Deploy a simple Tokenized URL
    await upsideProtocol.connect(owner).tokenize("https://code4rena.com/", await liquidityToken.getAddress());
    sampleLinkToken = await hhethers.getContractAt("UpsideMetaCoin", await upsideProtocol.urlToMetaCoinMap("https://code4rena.com/"));
  });

  it("should demonstrate the flaw of the C4 submission", async function () {
    await upsideProtocol.connect(owner).setFeeInfo({
      tokenizeFeeDestinationAddress: owner,
      swapFeeDecayInterval: 86400,
      tokenizeFeeEnabled: true,
      swapFeeStartingBp: 100, // 1 %
      swapFeeDecayBp: 10, // 0.1% decay
      swapFeeFinalBp: 10, // 0.1% final
      swapFeeSellBp: 100, // 1% sell fee
      swapFeeDeployerBp: 1000 // Deployer takes 10% of the sell fee
    });

    const attacker = user1;

    const victim = (await hhethers.getSigners())[3];

    for (let user of [attacker, victim]) {
      await liquidityToken.mint(user, ethers.parseUnits(1e6.toString(), 6));
      await liquidityToken.connect(user).approve(upsideProtocol, ethers.parseUnits(1e12.toString(), 6));
      await sampleLinkToken.connect(user).approve(upsideProtocol, ethers.parseUnits(1e12.toString(), 18));
    }

    const balLinkToken = ethers.parseUnits("1000000", 18);
    const balLiquidityToken = ethers.parseUnits("10000", 6);
    const inLiquidityToken = ethers.parseUnits("495", 6); // 500 USDC minus 1% fee
    const expectedOut = balLinkToken * inLiquidityToken / (balLiquidityToken + inLiquidityToken);

    const attackerInitialBalance = await liquidityToken.balanceOf(attacker);

    console.log("Expected output", expectedOut);

    // Attacker sees that there is a buy transaction in the mempool
    await upsideProtocol.connect(attacker).swap(sampleLinkToken, true, ethers.parseUnits("500", 6), expectedOut, attacker);

    // Victim's transaction goes through
    // Due to the high potential slippage - they set `expectedOut` at a reduction of 10% to the last price they observed
    await upsideProtocol.connect(victim).swap(sampleLinkToken, true, ethers.parseUnits("500", 6), expectedOut * BigInt(90) / BigInt(100), victim);

    // Attacker sells back the token
    await upsideProtocol.connect(attacker).swap(sampleLinkToken, false, expectedOut, 0, attacker);

    const attackerFinalBalance = await liquidityToken.balanceOf(attacker);

    console.log("Attacker profit", ethers.formatUnits(attackerFinalBalance - attackerInitialBalance, 6));
  });
});
```

Then run using yarn test --grep "C4 PoC Test Suite". Test logs show the attacker makes a profit of 36.44 USDC.

#### Recommendation
Consider fixing the `UpsideMetaCoin::transferFrom` function so that it actually restricts non-whitelisted users from calling `UpsideProtocol::swap` to perform a sell. Therefore in the earlier stages of the coin's life, this won't be an issue, until it becomes freely transferable. After it becomes a transferable token, you might want to consider adding a "cool down" period: after receiving some `UpsideMetaCoin` an address couldn't transfer it out until after the cool down period. This would add some technical complexity in order to deal with multiple transfers in to an address at different times, so it may not be worthwhile.

Additionally, the curve parameters lead to rapid price increases as shown. This may be desirable in some situations, but also leads to high potential slippage or griefing. You may want to consider adding an admin function to modify the initial liquidity parameters, or make it possible to change these parameters on a per-token basis to suit different situations (as arguments to `UpsideProtocol::tokenize`).

## 🟦 Low Severity Findings

**Submission details for all low severity findings:** https://code4rena.com/audits/2025-05-upside/submissions/S-465

### L-01: `UpsideProtocol::tokenize` can be front-run
On UpsideProtocol:118, it asserts that the given URL has not already been tokenized. It is possible for another user to front-run the transaction and tokenize the URL first, causing the other transaction to revert. If other users would tricked into using the resulting UpsideMetaCoin, the user who front-runned would then accumulate the deployer fees for this token. This is a low severity issue as this would incur a financial cost to the attacker, although potentially they could profit through deployer fees.

### L-02: Stakers do not contribute liquidity
Although the staking contract is not strictly part of this contest, it is worth noting that regardless of the staking contract implementation, the funds held in the staking contract do not directly add any liquidity to the protocol. Moreover, there is no way to directly add liquidity to the protocol on-chain i.e. there is no way to increase both `liquidityTokenReserves` and `metaCoinReserves` for a MetaCoin - we can only add to one and decrease the other. The impact is that the staked funds do not increase the `metaCoinReserves` which means they do not contribute to better prices for buyers

### L-03: `UpsideMetaCoin` does not maintain OpenZeppelin's special behaviour for setting allowance to `type(uint256).max`
The `UpsideMetaCoin` inherits from OpenZeppelin's ERC20 which has special behaviour when setting allowance to `type(uint256).max` as shown [here](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/e4f70216d759d8e6a64144a9e1f7bbeed78e7079/contracts/token/ERC20/ERC20.sol#L302). In this case, the allowance never decreases on spending. `UpsideMetaCoin` doesn't use this behaviour and instead just decreases the allowance on UpsideMetaCoin:83. This is not a huge issue but integrators might expect this special behaviour when approving `type(uint256).max`. You may want to instead only override the `_transfer` function (rather that `transfer` and `transferFrom`) by adding the `isTransferAllowed` modifier to it. This way you won't have to implement the allowance spending logic, and this can be left to the OpenZeppelin implementation.

### L-04: There is no way to change MetaCoin `deployer` address
In the unlikely event the the `deployer` address of a MetaCoin is compromised, there is no way to set it to a new address. You may want to consider a way for the admin and/or the deployer themselves to update this address to a new value.

### L-05: `UpsideProtocol::swap` can still be called with `_isBuy = true` after liquidity has been withdrawn
Even after the admin has called `UpsideProtocol::withdrawLiquidity` so the `metaCoinReserves` for the MetaCoin is set to zero, a user could accidentally call `UpsideProtocol::swap` with `_isBuy = true` and `_minimumOut = 0` and the function will not revert. Due to line 275, `amountOut` will be set to zero so they will receive zero MetaCoins back and lose their liquidity tokens to the protocol. It may be better to make this function revert early if `metaCoinReserves == 0`.

### L-06: `UpsideProtocol::claimableDeployerFees` does not need to be a nested mapping
This storage variable can be simplified:

```solidity
mapping(address metaCoinAddress => mapping(address walletAddress => uint256 deployerFeeClaimable))
        public claimableDeployerFees;
```

The reason is that the only the `walletAddress` which can accumulate fees is the deployer. The same functionality can
be implemented using:

```solidity
mapping(address metaCoinAddress => uint256 deployerFeeClaimable)
```

`UpsideProtocol::claimDeployerFees` would need to be updated so that it requires `msg.sender` to be the deployer.
